# HW-3 - сборочная линия на взаимодействующих процессах

Программа на C моделирует участок завода: детали обрабатываются на станках, проходят контроль качества, перевозятся роботами и собираются в изделия. Каждый участник линии - склад, станок, контролёр, робот, сборочный пост - работает в отдельном процессе. Процессы общаются через средства IPC POSIX: разделяемую память, семафоры и очереди сообщений.

Сделано четыре варианта программы, по одному на каждый уровень требований:

| Программа | Как запускаются процессы | Семафоры | Обмен данными |
|---|---|---|---|---|
| `line_unnamed` | родитель порождает участников через `fork()` | неименованные, в разделяемой памяти | разделяемая память |
| `line_named` | родитель порождает участников через `fork()` | именованные | разделяемая память |
| `shm_manager` + `shm_worker` | каждый участник - отдельно запущенная программа | именованные | разделяемая память |
| `mq_manager` + `mq_worker` | каждый участник - отдельно запущенная программа | именованные | очереди сообщений |

---

## 1. Сборка

```bash
cd HW-3
make
```

В папке `bin/` появятся шесть программ: `line_unnamed`, `line_named`, `shm_manager`, `shm_worker`, `mq_manager`, `mq_worker`. Предупреждений быть не должно.

```bash
make test     # автотесты всех четырёх вариантов (около минуты)
make clean    # удалить bin, результаты тестов и журналы
```

## 2. Как запускать

### Варианты 1 и 2 - одна команда

Родительский процесс сам создаёт процессы-участники:

```bash
./bin/line_unnamed -c configs/01_basic.cfg
./bin/line_named   -c configs/01_basic.cfg
```

### Варианты 3 и 4 - независимые процессы

Менеджер создаёт объекты IPC и ждёт участников, а каждый участник запускается отдельной командой.

Проще всего - скриптом, который запустит менеджера и всех участников сам:

```bash
./tests/run_independent.sh shm -c configs/01_basic.cfg     # вариант 3
./tests/run_independent.sh mq  -c configs/01_basic.cfg     # вариант 4
```

Вручную - так же, как это делает скрипт:

```bash
# терминал 1: менеджер
./bin/mq_manager -c configs/01_basic.cfg -d 200

# узнать, каких участников он ждёт
./bin/mq_manager -c configs/01_basic.cfg -L
#   warehouse 0
#   machine 0
#   ...

# терминалы 2, 3, ...: участники, по одному на команду
./bin/mq_worker warehouse 0
./bin/mq_worker machine 0
./bin/mq_worker robot 1
...
```

Моделирование начинается, когда подключатся все участники. Для `shm` всё то же самое, только программы `shm_manager` и `shm_worker`.

### Наглядная демонстрация

```bash
./tests/demo.sh named        # или unnamed, shm, mq
```

### Ключи менеджера (и `line_unnamed`, `line_named`)

| Ключ | Что делает | По умолчанию |
|---|---|---|
| `-c файл` | взять параметры из файла | встроенный сценарий «редукторы» |
| `-s число` | начальное значение генератора случайных чисел | из файла или по времени |
| `-d мс` | сколько миллисекунд длится единица модельного времени | 50 |
| `-l файл` | файл журнала; `-` - не писать | `line.log` |
| `-q` | тихий режим: на экран только итоги | выключен |
| `-t число` | лимит модельного времени | 1 000 000 |
| `-n имя` | имя объектов IPC (чтобы запускать несколько линий сразу) | `asm_line` |
| `-L` | только вывести список нужных участников | |
| `-h` | справка | |

Участники: `./bin/shm_worker [-n имя] <роль> <номер>`, роли - `warehouse`, `machine`, `inspector`, `robot`, `station`, номер - с 0.

## 3. Сигналы

Сигналы посылаются менеджеру (или `line_unnamed` / `line_named`):

| Сигнал | Команда | Что происходит | Код выхода |
|---|---|---|---|
| SIGINT | Ctrl+C | остановка всех процессов, итоги, удаление IPC | 130 |
| SIGTERM | `kill <pid>` | то же самое | 143 |
| SIGUSR1 | `kill -USR1 <pid>` | печать состояния линии, работа продолжается | - |
| SIGUSR2 | `kill -USR2 <pid>` | мягкая остановка: новые заготовки не выпускаются, детали в работе доделываются | 140 (или 0, если план успел выполниться) |

PID менеджера: `pgrep -f mq_manager` (или `line_named` и т. д.).

SIGTERM, посланный одному участнику (`pkill -f "mq_worker -n asm_line machine 3"`), завершает только его. Линия без этого участника встанет, и менеджер завершит работу с причиной «процессов-участников осталось 9 из 10».

## 4. Вывод программы

Сначала - параметры линии, затем подключение участников и события:

```
[t=    0] СИСТЕМА    Склад     процесс подключился (1 из 10)
...
[t=    0] СИСТЕМА    Линия     запуск: станков 5, контролёров 1, роботов 2, постов 1 - 10 процессов
[t=    2] СОЗДАНИЕ   Склад     создана деталь SHAFT#1, осталось заготовок 5
[t=   53] БРАК       ОТК-1     в HOUSING#9 обнаружен брак
[t=   53] СПИСАНИЕ   ОТК-1     HOUSING#9 списана: переделка не предусмотрена
   │          │          │       └ что произошло
   │          │          └ какой процесс (участник)
   │          └ вид события
   └ модельное время
```

| Событие | Когда |
|---|---|
| `СИСТЕМА` | процесс подключился / завершился, запуск линии, получен сигнал |
| `СОЗДАНИЕ` | склад выпустил заготовку |
| `ОЧЕРЕДЬ` | деталь поставлена в накопитель или очередь |
| `ПЕРЕВОЗКА` | робот взял или доставил деталь |
| `ОП.НАЧАЛО`, `ОП.КОНЕЦ` | станок начал / закончил операцию |
| `ПРОСТОЙ` | выход станка или ОТК заполнен - участник ждёт места |
| `КОНТРОЛЬ`, `БРАК` | проверка детали / найден брак |
| `ПЕРЕДЕЛКА`, `СПИСАНИЕ` | деталь возвращается на операцию / списана |
| `КОМПЛЕКТ` | деталь поступила в комплект для сборки |
| `СБОРКА`, `ВЫПУСК` | пост начал сборку / выпустил изделие |
| `!ИНВАРИАНТ` | нарушено правило модели (в нормальной работе не появляется) |

В конце - итоги: причина завершения, время, число процессов и событий, выпуск, средний цикл и такт, статистика по деталям, по каждому участнику (доля работы и простоя) и наибольшее заполнение накопителей. Всё пишется и в журнал `line.log`.

Процессы работают параллельно, поэтому два запуска с одинаковыми параметрами могут немного отличаться (брак может достаться другой детали). Итог при этом стабилен.

## 5. Варианты завершения

| Код | Итог | Когда |
|---|---|---|
| 0 | ПЛАН ВЫПОЛНЕН | выпущены все изделия по плану |
| 1 | ошибка | ошибка в файле, неверный ключ, нет файла |
| 2 | ИСХОДНЫЕ ДЕТАЛИ ИСЧЕРПАНЫ | заготовок не хватило (с учётом списаний) |
| 3 | ПРОИЗВОДСТВО НЕВОЗМОЖНО | невыполнимые данные, взаимная блокировка или ушёл процесс-участник |
| 4 | ПРЕВЫШЕН ЛИМИТ ВРЕМЕНИ | достигнут лимит `-t` |
| 5 | - | нарушены правила модели (ошибка программы) |
| 130 / 143 | ПРЕРВАНО СИГНАЛОМ | SIGINT / SIGTERM |
| 140 | МЯГКАЯ ОСТАНОВКА | SIGUSR2 |

При любом из этих вариантов разделяемая память, семафоры и очереди удаляются. Если процесс-менеджер убит через `kill -9` (это перехватить нельзя), остатки удалятся при следующем запуске с тем же именем `-n`.

## 7. Тесты

```bash
make test                     # все четыре варианта
./tests/run_tests.sh mq       # только один
```

Для каждого варианта проверяются: 10 сценариев, встроенный сценарий, лимит времени, отсутствующий файл, неверный ключ, события в журнале, подключение и завершение всех 10 процессов, сигналы SIGINT (всей группе процессов, как Ctrl+C), SIGTERM, SIGUSR1, SIGUSR2, а для независимых процессов - досрочный уход участника. После каждого прогона проверяется, что объекты IPC удалены. В конце должно быть `Итого: пройдено 86, не пройдено 0`.
